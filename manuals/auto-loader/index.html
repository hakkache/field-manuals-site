The organising idea

Almost every surprising thing Auto Loader does follows from one sentence: its unit of work is a new file at a new path.

Three consequences follow immediately. It is file-based — you cannot ask for only the rows changed since the last run; it reads a whole file or none of it. It is append-only — it has no concept of an update or a delete, and removing a file from the source does nothing to your table. And it is storage-only — no databases, no Kafka, no APIs. If there is no file, there is no Auto Loader.

Not a new record. Not changed contents. A path that the file registry has not seen before. Once that lands, the rest stops being surprising: editing a file in place changes nothing downstream, re-uploading the same data under a new prefix reprocesses all of it, and deleting the checkpoint does not "reset" the stream so much as create a different one.

The manual works outward from that sentence — through the architecture, then through the sixteen ways it goes wrong in production.

What the manual covers

  • Discovery: directory listing, incremental listing, file notification and managed file events — and the cost model of each.
  • The file registry, the checkpoint and the schema location: three pieces of state, and what happens when each is lost.
  • Schema inference, schemaHints, the evolution modes, and reading _rescued_data as a data quality signal.
  • Throughput controls, trigger choices, and running ingestion as a scheduled batch instead of continuously.
  • Backfills, migrations and multiplexed sources without duplicating history.

Six of the sixteen
failure modes.

Reproduced in full from the manual, in the same structure as the printed page. If these are useful, the other ten are in the free PDF.

Failure family · Schema Failure 01 of 16
Symptom
Your bronze table has amount, order_date and qty all typed as STRING. Every downstream cast fails, or silently returns null.
Cause
For JSON and CSV, cloudFiles.inferColumnTypes defaults to false. Auto Loader reads everything as a string on purpose, so that a single malformed value cannot poison a column's inferred type.
Fix
Turn inference on — or better, stop relying on inference for the columns that matter and name the types explicitly with cloudFiles.schemaHints. Careful: changing this on a running stream does not retroactively fix the stored schema. You must clear the schema location, the checkpoint and the table together, then reload.

Check first — Look at the stored schema under cloudFiles.schemaLocation rather than at the table — that is where the decision was actually made.

Failure family · State Failure 04 of 16
Symptom
Row count doubled overnight. No errors anywhere. Usually discovered by a business user noticing revenue is exactly 2×.
Cause
The checkpoint is the memory. Delete it and every file in the directory becomes new again, so the entire history is appended a second time.
Fix
Find the damage by grouping on the source file column, then roll back with Delta time travel — DESCRIBE HISTORY, then RESTORE TABLE to the version before the bad run. After that, reset the checkpoint and the table together and reload. The golden rule is that the checkpoint and the target table are one unit: reset both, or neither.

Check first — Group by your source-file column and look for files with more rows than expected. That query finds the blast radius in seconds.

Failure family · Discovery Failure 05 of 16
Symptom
You can see the file in the bucket. It is not in the table. Nothing errored, no alert fired, and the run was green.
Cause
Six independent causes produce this same silent symptom: incremental listing skipping files because it assumes lexicographically ordered filenames; a lost notification event; a case-sensitive glob filter excluding more than you meant; maxFileAge expiring the file before discovery; includeExistingFiles being false; or a hidden file starting with an underscore or a dot.
Fix
Work the list in that order — it is ranked by how often each turns out to be the culprit. Set useIncrementalListing to false if your filenames are not date-prefixed, set backfillInterval if you are on notification mode, and check the exact extension casing on your glob.

Check first — Capture _metadata.file_path and an ingestion timestamp as columns on every bronze table, then compare the count of distinct source files against the file count in storage. Two columns, zero cost, and the only way to detect this family at all.

Failure family · Schema Failure 02 of 16
Symptom
The job fails with a message about new fields found in the data, at unpredictable times — usually when an upstream team ships a release.
Cause
This is normal, intended behaviour of the default addNewColumns mode. Auto Loader saw an unknown column, saved the updated schema to the schema location, and stopped so that you notice.
Fix
Run the job with automatic retries so a schema change is a thirty-second self-heal rather than a pager alert. Then set mergeSchema on the write side too — otherwise Auto Loader evolves the schema successfully and the Delta write fails instead, which is a confusing half-fix.

Check first — The schema location holds a numbered history of every schema version. The diff between the last two tells you exactly which field arrived.

Failure family · Discovery Failure 07 of 16
Symptom
The vendor corrected a bad record and re-uploaded the file at the same path. Your table still shows the old values.
Cause
Same path means already seen, so it is skipped. This is by design — the path is the file's identity.
Fix
There is a partial fix and a real fix. cloudFiles.allowOverwrites makes Auto Loader reprocess a file when its modification time changes — but it appends rather than replaces, so you now hold both the old and the corrected rows and still need deduplication downstream. The real fix is to have the source write a new path and resolve versions with a MERGE in silver.

Check first — If the same bytes keep arriving at the same path, you have a snapshot problem rather than an incremental file problem. Solve it with MERGE or overwrite semantics, not with discovery options.

Failure family · Scale Failure 10 of 16
Symptom
The checkpoint directory is tens of gigabytes. Stream startup is slow and getting slower every week.
Cause
Auto Loader remembers every file it has ever seen, permanently. On a stream ingesting millions of files per hour, that state grows without bound.
Fix
Bound the state with cloudFiles.maxFileAge, and upgrade to a runtime where the stream no longer waits for the entire RocksDB state to download before starting. Understand the trade-off first: maxFileAge is a cost knob, not a correctness knob. The minimum accepted value is 14 days, and if a file older than the window ever appears — a very late delivery, a replayed archive — it is treated as brand new and ingested again.

Check first — Do the arithmetic before setting it. Two million files an hour over thirty days is roughly 1.4 billion entries, so confirm your real maximum arrival lateness rather than guessing.
