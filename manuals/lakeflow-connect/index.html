The organising idea

You configure it. You do not control it.

You choose the objects, the destination, the schedule, permissions and notifications. You cannot customise the ingestion process itself. That is the whole bargain — and it is why the repair for almost everything in the failure section is the same blunt instrument: a full refresh.

Seven documented causes end in one. That single fact is what makes prevention — retention headroom, gateway monitoring, small pipelines, coordinated schema changes — worth far more here than diagnostic skill.

What the manual covers

  • The four connector types — managed SaaS, database CDC, query-based and streaming — and two myths that will cost you a design review.
  • Two architectures: SaaS connectors have three parts, database CDC connectors have five, and those two extra parts cause most incidents.
  • The ingestion gateway: classic compute only, continuous mode, and the log-retention clock you are racing.
  • What "incremental" actually means per source, and why a cursor-based connector cannot see deletes.
  • Schema evolution you cannot configure, including the deleted column that breaks the pipeline months later.
  • Choosing between managed connectors, Auto Loader, Lakehouse Federation, Delta Sharing and building it yourself.
  • Sixteen documented failure modes with symptom, cause and fix, plus six production patterns and every documented limit.

Who it's for

Data and platform engineers evaluating managed ingestion, or already running it and trying to work out why a sync is behaving the way it is. It assumes you know what a pipeline is; it does not assume you have used Lakeflow Connect before.

Six of the sixteen
failure modes.

Reproduced from the manual, in the same structure as the printed page. If these are useful, the other ten are in the PDF.

Failure family · Gateway Failure 01 of 16
Symptom
After a maintenance window, a gateway restart or a long weekend, the pipeline reports missing changes — or destination tables are quietly out of step with the source.
Cause
The gateway was offline longer than the source's change log retention. Databricks can resume from where it left off only while the logs remain on the source. Once the source truncates them, the changes are gone.
Fix
Immediately, a full refresh of all affected tables — there is no incremental recovery path. For prevention, in order of value: raise retention on the source, never manually stop the gateway, and alert on gateway health directly rather than on pipeline success. On SQL Server the default is three days, which a long weekend can exceed.

Check first — Set the source's change retention to comfortably exceed your worst realistic outage — a long weekend plus a public holiday, not an average incident. It costs source storage, not DBUs.

Failure family · Operations Failure 13 of 16
Symptom
Someone removed an ingestion pipeline during a cleanup. The destination tables went with it, along with everything built on top of them.
Cause
The destination tables are dropped when the ingestion pipeline is deleted. This is documented behaviour, not an accident, and it is the single most dangerous fact in the product.
Fix
Prevention is the only real answer. Treat the destination schema as a disposable bronze landing layer and nothing else, build silver and gold in a separate schema with their own pipelines, restrict who can delete ingestion pipelines the way you would restrict destructive DDL, and make deletion a reviewed action rather than a cleanup task.

Check first — Ask which tables in that schema something else depends on structurally. Anything you cannot afford to lose should not live in a schema a managed pipeline controls.

Failure family · Schema Failure 09 of 16
Symptom
A pipeline that ran cleanly for months fails after a routine source change. Nobody deployed anything to Databricks.
Cause
A column was deleted at the source at some earlier point. Databricks did not delete it — it marked it inactive via a table property. When another column later appears with the same name, the pipeline fails.
Fix
Two documented options: trigger a full refresh of the affected table, or manually drop the inactive column from the destination table, which avoids the refresh. The second is usually much cheaper on a large table. The same behaviour applies at table level, so the same collision can happen with a reused table name.

Check first — This is the delayed family. A column deleted in March breaks the pipeline in June, when somebody unrelated reuses the name — so check the source's change history, not just the last deployment.

Failure family · Schema Failure 12 of 16
Symptom
Rows deleted at the source remain in the destination indefinitely, and a dropped source table is still present in Databricks.
Cause
Two separate causes with the same appearance. Cursor-based connectors cannot detect deletes — a deleted row simply stops appearing rather than generating an event. And when a source table is deleted the destination table is not automatically deleted; you must remove it manually.
Fix
Confirm your connector's delete semantics before designing around them, because CDC-based connectors detect deletes and cursor-based ones do not. Where deletes matter and the connector cannot detect them, schedule periodic full refreshes or reconcile against a source count. Add a manual cleanup step when source tables are decommissioned — nothing will prompt you.

Check first — If deletes matter to your business logic, and for anything financial or regulatory they do, verify the mechanism for your specific source rather than assuming every managed connector does native CDC.

Failure family · Gateway Failure 03 of 16
Symptom
A routine availability-group failover on the source database invalidated the entire pipeline, not just the tables that were mid-transaction.
Cause
Any source node change, including an AG failover, requires a full refresh of all tables in the pipeline. The connector's position in the change log is node-specific.
Fix
Accept the refresh, but size your pipelines with it in mind — a single pipeline carrying 200 tables means a 200-table refresh after every failover. Splitting into several gateway-and-pipeline pairs by domain limits the blast radius, at the cost of another gateway each. Coordinate with the DBA team so planned failovers are known events with a refresh scheduled after them.

Check first — Blast radius scales with pipeline size, and Databricks recommends 250 or fewer tables per pipeline. Both point the same way: smaller pipelines.

Failure family · Operations Failure 14 of 16
Symptom
A pipeline scheduled hourly appears to have run only every other hour. Nothing failed.
Cause
If update N is still running when update N+1 is scheduled, Databricks skips N+1 and picks up at N+2, assuming N completes in time. This is overlap protection, not an error.
Fix
Match the schedule to the actual runtime — if updates routinely take fifty minutes, an hourly schedule is fragile. Split large pipelines so each update finishes comfortably inside its window, and monitor update duration as a trend rather than just success or failure.

Check first — Skipped updates are invisible in a success-only view. Monitor destination table freshness directly instead; a table that has not updated within its expected window is the signal that arrives on time.
