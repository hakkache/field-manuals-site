The organising idea

A streaming query is a contract with its checkpoint.

The moment you start a query, the checkpoint fixes far more than most people realise — source identity by position in the plan, state schema, shuffle partition count, and the state store provider. Editing your code can break that contract, and the error arrives on restart rather than at deploy.

Almost every outage in this guide traces back to that single fact. Understand what the checkpoint locks and the sixteen failure modes stop being surprises — they become the predictable consequence of a contract you can read.

What the manual covers

  • The micro-batch model, and the stateless-versus-stateful distinction that decides how hard your query is to operate.
  • The checkpoint contract: what is inside a checkpoint, what it silently locks, and exactly which code changes survive a restart.
  • Streaming sources — Kafka, Kinesis, Event Hubs, Pub/Sub, Delta tables and Auto Loader — and how each handles offsets.
  • Triggers and batch size, including why the default trigger fails on serverless.
  • Watermarks and event time — the tuning dial between latency and tolerance for late data.
  • Stateful operations and the state store: aggregations, deduplication, stream-stream joins, RocksDB and changelog checkpointing.
  • Sixteen documented failure modes with symptom, cause and fix, plus production patterns, every documented limit, a checklist and a cheat sheet.

Who it's for

Data and platform engineers running streaming workloads, or debugging one that will not restart, grows state forever, or stops emitting rows. It assumes you can read a PySpark query; it does not assume you have operated Structured Streaming in production.

Six of the sixteen
failure modes.

Reproduced from the manual, in the same structure as the printed page. If these are useful, the other ten are in the PDF.

Failure family · Restart Failure 01 of 16
Symptom
A deploy that passed review fails on restart with a state schema or compatibility error. The code change looked harmless.
Cause
You changed something the checkpoint locks. Any addition, deletion or schema modification to a stateful operation is not allowed between restarts — grouping keys, aggregate types, join columns, join type, timeout type.
Fix
There is no in-place repair. Either revert the change and ship it differently with a side-by-side deploy, or start with a new checkpoint and accept that state is rebuilt and the source reprocessed. Prevention: if you expect the state schema to evolve, encode state as bytes with a schema-migration-capable format such as Avro, so the binary state restores cleanly across schema changes.

Check first — Treat grouping keys, aggregate types, join columns, join type and timeout type as part of the query's identity. If your diff touches any of them on a stateful operator, the old checkpoint will not load — plan a new checkpoint before you deploy, not after.

Failure family · State Failure 05 of 16
Symptom
A stateful query runs fine for weeks, then slows steadily and eventually fails with memory errors. Restarting helps briefly.
Cause
No watermark. Without one, state for every key is retained indefinitely — the engine has no basis for deciding a key is finished. This is the most common stateful streaming outage there is.
Fix
Add a watermark with withWatermark("event_time", "10 minutes") before the stateful operation. Caveat: adding a watermark to an existing query changes the stateful operation, which the checkpoint locks — so in practice this means a new checkpoint. Note that complete output mode never drops state, so on complete mode with a growing key space the mode itself is the problem.

Check first — Alert on state size per operator, not just on throughput. A stateful operator with no watermark grows without bound for weeks before it dies, and state size is where it shows up first — long before the memory error.

Failure family · Semantics Failure 10 of 16
Symptom
A stream-stream left outer join produces matched rows but never the expected null-padded unmatched ones — or produces nothing at all.
Cause
Watermarking is mandatory for outer joins. It is what tells the engine when an unmatched key must finally be written with a null. Without it — or without an appropriate range condition — the engine can never decide a row has waited long enough.
Fix
Set a watermark on both sides and add a time-range condition to the join so 'final' is well defined. Expect the delay: because joins only append, unmatched data is not recorded until after the lateness threshold has passed. Remember that stream-stream joins support append mode only.

Check first — An outer join is inherently later than the matched path — that is by design, not a bug. If unmatched rows are missing entirely, check that both sides carry a watermark and that the join has a time-range condition; without both, the engine never emits the null-padded side.

Failure family · Semantics Failure 11 of 16
Symptom
Counts do not reconcile against a batch recomputation. Some late-arriving events are simply not represented.
Cause
The watermark threshold is shorter than the actual lateness of your data. Records arriving outside the threshold might still be processed, but this is not guaranteed.
Fix
Measure real lateness before choosing a threshold — the distribution of (processing time − event time) at the 99th percentile, not the median. Lengthen the watermark, accepting more state and higher latency. Where completeness matters more than latency, run a periodic batch reconciliation against the raw source and treat the stream as the fast path rather than the authority.

Check first — Do not treat the watermark threshold as a limit on what might be handled — treat it as a promise about what will definitely be handled. If counts drift from a batch recompute, compare the threshold against the 99th-percentile lateness of your actual data.

Failure family · Semantics Failure 13 of 16
Symptom
Duplicate rows, duplicate API calls, or duplicate notifications after a failure and restart.
Cause
foreachBatch gives at-least-once semantics for your function. The same batch_id can be re-executed if the query fails between executing your code and committing the batch.
Fix
Make the function idempotent — a MERGE on a key is naturally so; a blind INSERT is not. Use batch_id for external side effects: record which batch IDs have been applied and skip on re-execution. Prefer toTable() where you can, since Delta sinks get exactly-once through the checkpoint without any of this.

Check first — If you see duplicates after a restart, look for a non-idempotent sink inside foreachBatch — a plain INSERT, an API call, or a notification. Any side effect that is not keyed on batch_id will fire twice when a batch is re-executed.

Failure family · Operations Failure 15 of 16
Symptom
A new query against an existing Kafka topic or large Delta table runs for hours, fails on memory, restarts, and repeats.
Cause
No rate limit. The first micro-batch attempts to consume everything the source retains — which for a Kafka topic with long retention can be months of events.
Fix
Set a rate limit: maxOffsetsPerTrigger for Kafka, maxFilesPerTrigger or maxBytesPerTrigger for Delta and Auto Loader. Rate limits are safe to add, change and remove across restarts. Combined with Trigger.AvailableNow, which processes a backlog across multiple rate-limited micro-batches, this is how you get through a large initial load without a single impossible batch.

Check first — If the first batch runs for hours against a source with a long history, there is no rate limit. Add maxOffsetsPerTrigger (Kafka) or maxFilesPerTrigger (Delta/Auto Loader) and the backlog drains across many bounded micro-batches instead of one unbounded one.
